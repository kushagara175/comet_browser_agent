## What Will Differentiate You

### 1. Multi-modal privacy detection

Most teams will probably demonstrate only obvious HTML password fields. That is not sufficient.

Use three local detection paths:

- **DOM and accessibility analysis**
  - `input[type=password]`
  - `autocomplete` attributes
  - `name`, `id`, `aria-label`, labels and nearby text
  - hidden form metadata
  - email, phone, OTP, card, PAN and Aadhaar-like patterns using local rules

- **Local visual detection**
  - faces
  - ID cards
  - signatures
  - visually sensitive regions
  - UI components rendered without useful DOM labels

- **Local OCR**
  - PII inside screenshots
  - images
  - canvas elements
  - PDFs rendered in the browser
  - text inside charts or scanned documents

Your privacy mask should be the union of all three detection methods:

```text
Final Sensitive Region =
DOM detections
+ OCR detections
+ visual-model detections
+ policy rules
```

If any detector is uncertain, default to blocking or redacting the region. This is more credible than claiming that your model will never miss anything.

### 2. Fail-closed egress protection

Your strongest differentiator should be a local egress gate.

The pipeline should be:

```text
Page DOM / screenshot
        |
Local perception
        |
PII and sensitive-region detection
        |
Redaction and semantic replacement
        |
Privacy policy validation
        |
Sanitized payload only
        |
Server reasoning
```

The server should never receive the original screenshot, original DOM, password value, raw name, raw email or original OCR text.

The extension should construct the server request itself. Do not allow page JavaScript or the webpage's own network code to send the agent context directly to your server.

Be precise about your claim:

> “We protect the context generated for our AI agent. We do not claim to block every network request made independently by the webpage.”

That answer is technically honest. Claiming that your extension prevents every request from every website will invite difficult questions.

### 3. Semantic redaction instead of simple blurring

If you simply blur everything, the server may not understand the page.

Replace sensitive values with semantic tokens while preserving layout and task relevance:

```text
"Rahul Sharma"       -> [PERSON_01]
"rahul@gmail.com"    -> [EMAIL_01]
"982xxxxx321"        -> [PHONE_01]
"********"           -> [PASSWORD_FIELD]
"4111 1111 1111..."  -> [CARD_NUMBER]
```

The sanitized representation can contain:

```json
{
  "type": "EMAIL",
  "id": "EMAIL_01",
  "bbox": [420, 210, 180, 32],
  "role": "input",
  "editable": true
}
```

It must not contain the original email value.

This allows the server to understand:

- that an email field exists
- where it is located
- whether it is editable
- what nearby buttons and labels mean
- what action is safe to propose

For high-risk text, use opaque masking rather than reversible blur. Blur is appropriate only when the task requires preserving the approximate visual appearance of a face or object.

### 4. Safe action execution

The server should not return arbitrary JavaScript.

Use a typed action schema:

```json
{
  "action": "CLICK",
  "target": {
    "role": "button",
    "text_token": "SUBMIT",
    "bbox": [700, 500, 110, 40]
  },
  "confidence": 0.94,
  "requires_confirmation": true
}
```

Allow only bounded operations:

- `CLICK`
- `SCROLL`
- `SELECT`
- `OPEN_TAB`
- `READ_NON_SENSITIVE_TEXT`
- `TYPE_NON_SENSITIVE_TEXT`

Do not allow:

- arbitrary JavaScript execution
- direct cookie access
- access to password values
- typing into password fields
- cross-origin page actions without explicit policy
- automatic submission of destructive forms

Before executing an action, the local extension should verify:

- the same tab is still active
- the page origin has not changed unexpectedly
- the target still matches the original element
- the action is allowed by policy
- the target is not sensitive
- confirmation is required for submit, delete, transfer or login actions

Browser agents face prompt-injection and cross-origin risks because webpage content can be misinterpreted as instructions. Recent research has demonstrated that malicious webpages can attempt to influence agent actions and cross-origin data handling. Treat all webpage content as untrusted data, not as instructions. ([agent-security.cs.washington.edu](https://agent-security.cs.washington.edu/agentic_browsers_sop.html))

### 5. Resource-aware model routing

Use a small local model, not a large local VLM.

Recommended architecture:

```text
WebGPU available?
        |
      Yes -> quantized ONNX vision model using WebGPU
        |
      No  -> WASM CPU fallback
```

ONNX Runtime Web supports browser inference through WebAssembly and has WebGPU integration. Its current documentation shows WASM support across Chrome and Firefox, while WebGPU support is more limited depending on browser and platform. This makes feature detection and a WASM fallback important. ([onnxruntime.ai](https://onnxruntime.ai/docs/get-started/with-javascript/web.html))

Do not say:

> “Our model works on every browser with WebGPU.”

Say:

> “We use WebGPU where available and fall back to WASM. We benchmark both modes separately.”

Use:

- quantized ONNX model
- reduced screenshot resolution
- region-of-interest processing
- tile-based inference
- model warm-up
- cached DOM features
- `MutationObserver` to process only changed regions
- lazy loading of OCR and face models
- no continuous full-resolution screen analysis unless required

Do not use real personal data. Use synthetic data with ground-truth bounding boxes and labels.

Report:

| SIH metric | What you should measure |
|---|---|
| Visual context accuracy | Correct identification of buttons, fields, labels and regions |
| PII precision/recall | Results separately for password, email, phone, face, card and ID-like data |
| Redaction precision | How much of the sensitive region is correctly masked without masking unrelated content |
| Resource utilization | Model size, peak RAM, CPU/GPU time, browser startup cost |
| End-to-end latency | Capture to sanitized payload, server reasoning, action validation and execution |


If you have not measured a value, leave it out rather than inventing it.

## Judge Questions

Use the following as your mock-viva sheet. Replace bracketed values with your actual measurements.

### Problem Understanding

**Question:** What exactly is the problem?

**Expected answer:**

> Current browser agents may send screen state or page context to a server for reasoning. This creates a privacy risk. A full local vision-and-reasoning pipeline may be too heavy for ordinary devices. Our solution keeps perception and sensitive-data detection local, sends only sanitized context for heavy reasoning, and executes actions locally.

**Question:** What do you mean by “screen state”?

**Expected answer:**

> We treat screen state as a combination of rendered pixels, DOM structure, accessibility metadata and action-relevant page state. DOM alone is insufficient because sensitive content may appear inside images, canvas elements or visually rendered documents.

**Question:** Are you protecting all browser traffic?

**Expected answer:**

> No. Our scope is the context generated for the AI agent. The extension owns the agent's outbound request and ensures that only sanitized context is sent. We do not claim to block independent network requests made by the webpage itself.

**Question:** Why not simply keep the entire AI model local?

**Expected answer:**

> A full visual-language reasoning model can be too expensive for ordinary browser devices. We keep lightweight perception and privacy enforcement local, while sending only anonymized context to a server for heavier reasoning.

### Privacy and Redaction

**Question:** What happens if your detector misses a password or PII?

**Expected answer:**

> We do not rely on one detector. We combine DOM semantics, OCR, visual detection and policy rules. If the detectors disagree or confidence is insufficient, the privacy policy fails closed by blocking the request or redacting the larger uncertain region.

**Question:** What happens if you over-redact?

**Expected answer:**

> We preserve layout, role and semantic category through tokens such as `[EMAIL_01]` or `[PASSWORD_FIELD]`. This allows the server to reason about the page without seeing the original value. We measure both privacy recall and redaction precision because protecting privacy by hiding the entire page would not solve the task.

**Question:** Is blur enough for privacy?

**Expected answer:**

> Not for high-risk text. Passwords, emails and identifiers are replaced with opaque masks or semantic tokens. Blur or pixelation is used only where visual shape must be retained, such as a face region needed for layout understanding.

**Question:** Can the server reconstruct the original value?

**Expected answer:**

> The server receives neither the original text nor reversible encryption keys. It sees only category tokens, geometry and safe structural information. The local browser retains the original page state.

**Question:** How do you prove that raw PII was not transmitted?

**Expected answer:**

> The server request is created only after the local sanitizer and egress verifier run. We test with synthetic canary values, inspect outbound requests, fuzz payloads, and maintain an automated test that fails if raw PII appears in JSON, HTML, screenshots, URLs or logs.

**Question:** Can you guarantee zero leakage?

**Expected answer:**

> We do not make an unrestricted claim of mathematical perfection. Our bounded claim is that, under our defined threat model, the extension's agent-generated request contains only sanitized representations. We support this claim with architecture, automated leakage tests and adversarial cases.

### Technical Architecture

**Question:** Why combine DOM and vision?

**Expected answer:**

> DOM analysis is reliable for semantic fields such as password inputs and labels. Vision and OCR handle canvas, images, scanned documents and visually rendered content. Combining both improves coverage.

**Question:** Why use a ViT or equivalent model?

**Expected answer:**

> The local model provides visual understanding of page regions and UI elements that cannot be recovered reliably from DOM metadata. We use a quantized lightweight model because SIH evaluates resource utilization as well as accuracy.

**Question:** Why ONNX Runtime Web?

**Expected answer:**

> It gives us a browser-compatible inference runtime with WebAssembly and WebGPU execution paths. We can use GPU acceleration when available and fall back to CPU inference when it is not. ([onnxruntime.ai](https://onnxruntime.ai/docs/get-started/with-javascript/web.html))

**Question:** Will it work in Firefox?

**Expected answer:**

> We use feature detection. If WebGPU is available, we use it. Otherwise, we use the WASM path. We report Chrome-WebGPU, Chrome-WASM and Firefox-WASM results separately instead of claiming identical performance on every platform.

**Question:** What if the page changes while the model is processing?

**Expected answer:**

> We attach a page-state version and element fingerprints to the observation. Before executing an action, the local validator re-checks the current DOM and target geometry. If the page has changed materially, the action is rejected and the page is re-analyzed.

**Question:** How do you handle iframes?

**Expected answer:**

> We maintain frame and origin boundaries. Same-origin frames can be analyzed according to the extension policy. Cross-origin frames are treated as separate security contexts and are not automatically read or acted upon without explicit permission.

**Question:** How do you handle PII in URLs, image metadata or accessibility labels?

**Expected answer:**

> The sanitizer covers more than the screenshot. It removes or tokenizes sensitive text in DOM attributes, accessible names, URLs, OCR output and structured metadata before constructing the payload.

### Agent Security

**Question:** What prevents a malicious webpage from giving instructions to your agent?

**Expected answer:**

> Webpage content is data, not authority. We separate the user's instruction from page content, attach provenance to observations, ignore webpage attempts to redefine agent policy, and allow only a typed action schema. The local executor validates every action.

**Question:** Why not let the LLM return JavaScript?

**Expected answer:**

> Arbitrary JavaScript would defeat the security boundary. The server returns only bounded actions such as click, scroll or select. The extension performs local target validation and never executes arbitrary server-provided code.

**Question:** What happens if the server is compromised?

**Expected answer:**

> The server still does not receive raw PII. A compromised server can at most return a malicious action proposal, which must pass the local action policy. High-risk operations require user confirmation.

**Question:** Can the agent enter a password?

**Expected answer:**

> No. Password fields are treated as protected targets. The agent may detect their presence, but it cannot read, transmit or fill them.

### Evaluation

**Question:** How did you measure visual-context accuracy?

**Expected answer:**

> We use annotated webpages with ground-truth roles, labels, bounding boxes and action targets. We report element grounding accuracy and action-target accuracy on pages excluded from training and threshold tuning.

**Question:** How did you measure PII recall?

**Expected answer:**

> We calculate recall separately for each category, including passwords, emails, phone numbers, faces, card-like numbers, ID-like text and image-based PII. We also report precision so that the system is not simply hiding the entire page.

**Question:** What is redaction precision?

**Expected answer:**

> It measures how accurately the redaction covers sensitive regions while avoiding unrelated content. We report region-level overlap, pixel-level overlap where applicable, false masking and known leakage cases.

**Question:** What is your latency?

**Expected answer:**

> We separate cold-start model loading from warm inference and report p50 and p95 values for capture, local detection, redaction, network reasoning, validation and execution. Our slide contains the measured values, not estimates.

**Question:** How much memory does your extension consume?

**Expected answer:**

> We report the model artifact size, peak additional browser memory, CPU/GPU utilization and inference time on at least one low-resource and one higher-resource machine.

**Question:** How do you test generalization?

**Expected answer:**

> We test on held-out layouts, domains, themes, fonts, zoom levels, mobile dimensions, dynamic pages, image-based PII, canvas content, iframes and adversarial prompt-injection text.

### Feasibility and Deployment

**Question:** What is already working?

**Expected answer:**

> We demonstrate one complete path: webpage loading, local detection, redaction, sanitized network payload, server-generated typed action, local validation and browser execution. We clearly label what is implemented and what remains planned.

Do not answer this with a list of technologies.

**Question:** Can this be deployed without your cloud provider?

**Expected answer:**

> Yes. The server reasoning layer is replaceable with a self-hosted open-weight model. The client-side privacy layer remains independent of the model provider.

**Question:** What extension permissions do you require?

**Expected answer:**

> We use the minimum permissions needed for the selected workflow. We avoid cookie access, password-manager access and unnecessary broad permissions. The extension's permission list is shown in our documentation.

**Question:** What are your model licenses?

**Expected answer:**

> We list the exact model, runtime and dataset licenses. We do not include a model in the final prototype until we verify that its license permits the intended use.

### ISRO Relevance

**Question:** Why is this relevant to ISRO?

**Expected answer:**

> The problem combines privacy-sensitive data, autonomous decision-making and resource-constrained local computation. These are relevant to secure engineering and operational workflows. Our architecture is modular, explainable at the action level, fault-aware and capable of operating with a self-hosted or isolated reasoning server. We are not claiming direct ISRO deployment; we are demonstrating a transferable technical architecture.

Official ISRO research material on intelligent agents emphasizes real-time reliable and interpretable decision-making, modular architecture, interaction with diverse information and future autonomous operation. Those are good design principles for your project, even though they are not a published SIH26171 scoring rubric. ([isro.gov.in](https://www.isro.gov.in/media_isro/pdf/programme/respond_basket_2022.pdf?utm_source=openai))

**Question:** What does “autonomous” mean in your project?

**Expected answer:**

> Autonomy is bounded. The system can perceive, reason and propose actions, but local policy controls what may execute. High-risk actions require confirmation. We prioritize predictable and verifiable behavior over unrestricted autonomy.

**Question:** What is your biggest failure mode?

**Expected answer:**

> The most serious failure is transmitting sensitive content because of a missed detection. Therefore, our design prioritizes high recall, multi-modal detection, fail-closed behavior and automated leakage testing, even if this occasionally reduces task completion.

That answer demonstrates that you understand the actual risk.

## ISRO Evaluator Expectations

An ISRO-oriented evaluator is likely to care less about attractive UI and more about engineering discipline.

Show these qualities:

- **Resource awareness:** model size, RAM, CPU/GPU time and browser fallback
- **Reliability:** behavior when the model fails, browser changes or network disappears
- **Explainability:** why a region was redacted and why an action was executed
- **Modularity:** detector, policy engine, server reasoner and executor should be replaceable
- **Security:** least privilege, no raw data in logs, no arbitrary code execution
- **Reproducibility:** dataset generation, model version, test cases and benchmark script
