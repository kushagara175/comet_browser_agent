# SIH26171 — Winning Execution Playbook

## Privacy-Preserving On-Device Visual Perception for Lightweight Browser Agents

Status: implementation authority  
Prepared: 28 August 2026  
Audience: product owner, engineering team, coding agents, demo team, and reviewers

---

## 0. Purpose

This is the single source of truth for building SIH26171.

It turns the existing high-level plans into a buildable, testable, judge-ready product plan.

The repository currently contains planning documents only.

There is no extension source code, server implementation, model asset, benchmark harness, or proof that raw data cannot leave the browser.

Treat the work as a greenfield build.

The winning claim is:

> Every artifact that crosses the browser privacy boundary is generated by a fail-closed local sanitization pipeline, while the agent can still complete a useful task from the sanitized context.

Do not claim merely that the demo blurs obvious fields.

## 2. Product definition

Working product name:

    PrivaPilot

Tagline:

    A browser agent that sees enough to help, but never sends what it should not see.

### 2.1 User promise

1. The user enters a goal and explicitly starts the run.
2. The extension observes only the active tab.
3. It detects and redacts sensitive content locally.
4. It produces a sanitized screenshot and compact sanitized element list.
5. Only those sanitized artifacts go to the server.
6. The server returns one proposed next action.
7. The client validates that proposal locally.
8. The client auto-executes only safe, reversible actions.
9. The user approves meaningful or irreversible actions.

### 2.2 MVP non-goals

The MVP does not:

- bypass CAPTCHA, login, MFA, or anti-bot controls;
- send passwords, OTPs, cookies, tokens, raw HTML, raw DOM, or raw screenshots;
- auto-submit forms;
- auto-click payment, deletion, publication, signing, authorization, or account-security controls;
- claim cross-origin iframe DOM access;
- claim image or canvas text redaction before it exists and is benchmarked;
- claim universal browser automation.

### 2.3 Winning demonstration

A credible demo must show:

1. Raw context remains local.
2. A visibly different sanitized version is what crosses the network boundary.
3. A network inspection/test proxy shows no fixture secret.
4. The server returns a useful action from sanitized context.
5. The browser executes a useful safe action.
6. A protected action requires confirmation.
7. An unsupported surface fails closed.
8. Every displayed metric has reproducible measurement provenance.

### 2.4 Recommended demo scenario

Build a self-hosted portal with synthetic data:

- profile photo containing a face;
- visible synthetic email;
- visible synthetic phone number;
- password field;
- credit-card-like synthetic number in ordinary text;
- search/filter task;
- safe preview action;
- disabled protected Submit action.

Use a harmless goal such as:

    “Find the request with Pending status and open its safe preview.”

The primary demo must not need real user credentials.

## 3. Privacy contract

### 3.1 The boundary

The final sanitizer is the privacy boundary.

No screenshot, DOM fragment, OCR result, accessibility name, error object, analytics event, audit record, or action log may cross the network before sanitization.

Represent this in code:

    RawCapture -> DetectionReport -> SanitizedContext -> NetworkPayload

The HTTP client accepts SanitizedContext only.

RawCapture must not be assignable to the server client.

### 3.2 Fail closed

If coverage is uncertain, do not transmit the screenshot.

Display:

    “Sensitive content may be present in an area that cannot be inspected safely. No context was sent.”

Safe options:

- use a DOM-only sanitized summary;
- let the user locally hide the region;
- let the user add a local redaction rectangle;
- cancel.

Never send raw capture after a timeout or model failure.

### 3.3 Data classes

Never leave browser:

- passwords;
- OTPs;
- tokens and API keys;
- cookies;
- credit-card numbers and CVVs;
- bank accounts;
- Aadhaar, PAN, and government IDs;
- authentication QR codes;
- medical identifiers.

Redact by default:

- emails;
- phone numbers;
- addresses;
- faces;
- names where context makes them personal;
- employee IDs;
- dates of birth;
- profile photos;
- sensitive free text.

Server-permitted after minimization:

- locally assigned element IDs;
- roles;
- sanitized names;
- normalized bounds;
- enabled/visible state;
- action capabilities;
- redacted screenshot;
- sanitized goal.

Never collect for MVP:

- full HTML;
- raw DOM;
- clipboard;
- history;
- local storage;
- credential manager contents;
- devtools data.

### 3.4 Audit data rule

Never retain raw sensitive data or hashes of it.

A hash of an email, phone number, or known ID can still be guessable.

Audit records may contain:

- timestamp;
- category;
- local bounding box;
- detector source;
- redaction method;
- capture ID;
- sanitized-payload digest;
- blocked/allowed decision.

### 3.5 Visual redaction rule

Use opaque masks for text, controls, unknown graphics, images with text, canvases, and uninspectable surfaces.

Use blur only for confidently detected faces, with substantial padding.

After rendering, run local post-redaction checks.

If a sensitive region remains, expand the mask or block the upload.

### 3.6 High-risk surfaces

Treat these as high risk:

- cross-origin iframes;
- closed shadow roots;
- canvas and WebGL;
- video;
- images containing text;
- SVG text;
- CSS pseudo-element text;
- browser-native UI;
- PDF viewers.

If visual coverage for a high-risk surface is absent, mask its full rectangle or block screenshot upload.

Lack of DOM text does not mean the surface is safe.

## 4. Build architecture

### 4.1 Browser compatibility

Use a WebExtensions-compatible core.

Do not rely on Chrome offscreen documents as the mandatory cross-browser sanitizer runtime.

Chrome-specific code must be isolated behind an adapter.

Required flow:

    content script
      -> browser adapter
      -> background coordinator
      -> local sanitizer
      -> SanitizedContext
      -> server adapter
      -> validated action
      -> content executor

In Chrome, an offscreen document may host the model.

In Firefox, use a proven supported worker/page approach.

Privacy correctness must not depend on WebGPU.

WebGPU is an accelerator.

WebAssembly or CPU fallback is the correctness path.

### 4.2 Responsibilities

Content script:

- extract permitted local DOM signals;
- create local element IDs;
- calculate geometry;
- render local overlays;
- execute validated actions;
- observe DOM mutations.

Background coordinator:

- own one run per tab;
- capture active-tab screenshot;
- pair capture and DOM state;
- call the server;
- reject raw artifacts;
- write sanitized audit entries.

Sanitizer:

- run local detectors;
- convert coordinates;
- merge regions;
- render masks;
- scrub DOM text;
- run post-redaction checks;
- return SanitizedContext or a block reason.

Side panel:

- receive explicit consent;
- show raw data locally only;
- show outgoing sanitized context;
- display action proposal and confirmation;
- display measured telemetry.

Server:

- validate a closed request schema;
- call a configurable compatible model;
- return one validated action;
- persist nothing by default;
- never request raw data.

### 4.3 Repository layout

Create this before feature coding:

    apps/
      extension/src/
        background/
        browser/
        content/
        sanitizer/
        shared/
        sidepanel/
      server/src/
      demo-portal/src/
    packages/
      protocol/
      pii-rules/
      test-fixtures/
      benchmark/
    docs/
      decisions/
      evidence/
      benchmark-results/
    tests/
    scripts/

### 4.4 Minimum model plan

MVP local model:

- one bundled, quantized face detector.

MVP deterministic local detectors:

- DOM semantic detector;
- local visible-text PII detector;
- sensitive attribute detector;
- uninspectable-surface detector.

Stretch:

- local OCR or text-region detector for image/canvas/PDF text.

Do not begin with a generic local ViT just to satisfy a keyword.

The local face model plus local privacy perception is a real, demonstrable local vision component.

### 4.5 Capture and coordinate contract

Every detection must name its coordinate space:

    screenshotPixel
    viewportCssPixel
    documentCssPixel

For each capture, record:

- viewport CSS width and height;
- screenshot pixel width and height;
- device pixel ratio;
- scroll offsets;
- visual viewport offsets;
- capture timestamp.

Conversion:

    screenshotX = viewportX * screenshotWidth / viewportWidth
    screenshotY = viewportY * screenshotHeight / viewportHeight

Then clamp and add padding.

Test DPR 1, 1.25, 1.5, 2, and 3.

The background process must obtain the screenshot.

The content script supplies DOM geometry.

If resize, scroll, navigation, or visibility changes between the two, discard and retry.

Never combine stale DOM geometry with a newer screenshot.

### 4.6 Sanitized element contract

Do not send raw CSS selectors.

Do not send IDs, classes, hrefs, data attributes, raw labels, or raw values by default.

The server receives compact interactive elements:

    {
      "localId": "el_7",
      "role": "button",
      "sanitizedName": "Open preview",
      "coarseBounds": [0.61, 0.72, 0.18, 0.06],
      "state": ["enabled", "visible"],
      "actionCapabilities": ["click"]
    }

The local extension resolves localId to the real DOM element.

### 4.7 Network payload

The payload must be versioned and closed:

    {
      "protocolVersion": "1.0",
      "runId": "random-uuid",
      "goal": "sanitized user goal",
      "screenshot": "sanitized-image-only",
      "elements": [],
      "pageState": {
        "title": "sanitized title",
        "viewport": [1280, 720]
      }
    }

Reject unknown keys.

In tests, serialize every outgoing payload through a canary scanner.

### 4.8 Action protocol

The server proposes one action only.

Allowed kinds:

    observe
    click
    type
    select
    scroll
    wait
    request_user_confirmation
    finish
    blocked

Required action fields:

    actionId
    kind
    targetLocalId
    confidence
    risk
    rationale
    expectedState

The server must not return CSS selectors, JavaScript, arbitrary URLs, passwords, OTPs, or sensitive text.

The client validates every action against the current local sanitized state.

## 5. Detection and redaction design

### 5.1 Fusion rule

Use the union of all detector results.

If any detector flags a region, redact it.

False positives are preferable to privacy false negatives.

### 5.2 DOM semantic detector

Inspect locally:

- input type;
- autocomplete;
- inputmode;
- name and id;
- aria-label;
- associated labels;
- placeholders;
- nearby visible text;
- role;
- form context.

Categories:

- password;
- email;
- phone;
- credit card;
- CVV;
- bank account;
- national ID;
- date of birth;
- address;
- username;
- authentication code;
- token.

Use token rules, not careless substring matching.

Store reasons locally for review.

### 5.3 Local text PII detector

Minimum pattern families:

- email;
- Indian/international phone;
- PAN;
- Aadhaar-like number;
- card candidate with Luhn validation;
- CVV only in card context;
- account/ID candidate only with high-confidence context.

The detector returns category and local offsets.

It must never log the matched string.

### 5.4 Face model

Run locally on the screenshot.

Use:

- confidence threshold;
- non-maximum suppression;
- clipped bounds;
- category-specific padding.

Test frontal, profile, thumbnail, multiple, small, partial, avatar, artwork, and video-frame cases.

### 5.5 Canvas/image/PDF plan

Existing plans do not safely cover image text, canvas, video, PDF, or cross-origin frames.

MVP policy:

- mask the whole risky surface; or
- block screenshot transmission.

Phase-two policy:

- local OCR;
- PII matching on OCR output;
- mask risky OCR boxes;
- mask whole surface on low confidence.

### 5.6 Region algorithm

1. Normalize all boxes into screenshot pixels.
2. Add padding.
3. Clamp to image bounds.
4. Merge overlapping regions.
5. Render opaque masks or face blur.
6. Create local manifest.
7. Run post-redaction verification.

### 5.7 Post-redaction checks

At minimum:

- opaque masks cover all sensitive DOM rectangles;
- expected mask pixels are present;
- fixture secrets are absent from sanitized DOM summary;
- residual confident faces are not visible;
- high-risk surfaces are masked or blocked.

## 6. Reasoning and execution

### 6.1 Server behavior

The server is a stateless adapter.

Disable request-body logging in demo mode.

Redact headers and errors.

The system prompt must say:

- redactions are intentional;
- never ask for unredacted content;
- choose one action;
- use local IDs only;
- express uncertainty;
- request confirmation for protected actions;
- return schema-valid JSON only.

Invalid model output procedure:

1. Do not execute.
2. Record a local redacted diagnostic.
3. Optionally make one schema-repair attempt.
4. If still invalid, show a safe error.

Never parse arbitrary prose into an action.

### 6.2 Action policy

Auto-allow:

- scroll;
- focus non-sensitive field;
- click harmless navigation;
- open preview;
- select non-sensitive filter;
- type user-provided non-sensitive search text.

Require user confirmation:

- submit;
- send;
- publish;
- delete;
- save;
- download;
- upload;
- pay;
- purchase;
- sign;
- authorize;
- account/security changes;
- typing in sensitive field.

Always block:

- CAPTCHA;
- MFA/OTP entry;
- password entry from server;
- secret pasting;
- browser permission prompts;
- extension pages;
- local-file access.

### 6.3 State verification

pHash difference alone is not enough.

Use:

- expected semantic outcome;
- target/landmark mutation;
- visibility or enabled-state change;
- URL state where relevant;
- screenshot change only as corroboration;
- bounded timeout.

Success means:

    “Preview panel became visible.”

Not:

    “The image changed enough.”

### 6.4 Executor rules

Before a click:

- target exists;
- target is visible and enabled;
- local ID still maps to correct semantic role;
- target is not protected;
- current capture is fresh.

Use DOM execution first.

Treat coordinate click as experimental fallback only.

For typing, use non-sensitive user text and framework-compatible input handling.

For selects, validate against current local options.

After a scroll, re-capture and re-sanitize.

## 7. Benchmark strategy

### 7.1 Measurement requirements

Every result requires:

- metric definition;
- fixed corpus;
- ground truth;
- reproducible command;
- stored safe result;
- report with failures.

Never show live “PII recall” based on a single page without ground truth.

### 7.2 Visual-context accuracy

Measure:

- actionable-element recall;
- actionable-element precision;
- role accuracy;
- median bounding-box IoU;
- task-grounding success.

Define ground truth per fixture.

### 7.3 PII detection

Measure recall and precision separately for:

- password fields;
- emails;
- phones;
- cards;
- IDs;
- faces;
- image-text PII;
- canvas/frame behavior.

Publish failed cases, not only aggregate figures.

### 7.4 Redaction precision

Measure:

- sensitive-region coverage;
- under-mask count;
- over-mask area;
- preservation of safe actionable controls;
- residual detector findings.

### 7.5 Resource utilization

Measure:

- model load;
- DOM extraction;
- detector time;
- render time;
- payload generation;
- JS heap delta where available;
- GPU metrics only where the browser exposes trustworthy data.

Label browser-specific instrumentation honestly.

### 7.6 Latency

Timestamp:

    t0 run starts
    t1 capture complete
    t2 detection complete
    t3 sanitized payload validated
    t4 reasoning response received
    t5 action validated
    t6 action completed
    t7 state verified

Report p50 and p95 across at least 30 runs per fixture/device.

Separate cold and warm runs.

### 7.7 Fixture corpus

Build synthetic fixtures containing no real PII.

Required families:

- standard login;
- misleading field names;
- payment;
- profile with PII;
- face gallery;
- image PII;
- canvas PII;
- cross-origin iframe placeholder;
- shadow DOM;
- controlled React input;
- long scroll;
- dark mode;
- zoom/DPR variants;
- cookie banner;
- modal.

Use a known fixture canary:

    SECRET_CANARY_SIH26171_DO_NOT_TRANSMIT

Fail any test if that string appears in URL, headers, body, logs, analytics, or exceptions.

### 7.8 Launch gates

- No fixture secret in network capture.
- No raw image in network capture.
- All password fixtures masked.
- High-risk surfaces masked or blocked.
- No protected action without confirmation.
- Stable safe task completion on primary portal.
- Unsupported cases fail closed.

## 13. Jury answers

Why use a server?

    The browser owns privacy enforcement and lightweight perception. The server reasons over only sanitized layout, enabling useful assistance on constrained machines.

What happens when detection is uncertain?

    The system fails closed: it masks the region or blocks screenshot upload.

How do you prove nothing sensitive is sent?

    Closed schemas, a test proxy, fixture canaries, and local audit metadata prove the request path without storing raw values.

Does it work everywhere?

    We do not claim universality. We show documented coverage across varied fixtures and fail closed on unsupported surfaces.

Why local IDs instead of CSS selectors?

    Local IDs minimize implementation exposure and prevent a remote model response from arbitrarily targeting the page.

What if the model says Submit?

    Submission is a protected action and requires the user’s confirmation.

What if WebGPU is unavailable?

    It is an accelerator only. A local fallback preserves privacy, or screenshot upload is blocked.

What about text inside images?

    Until local OCR is benchmarked, those surfaces are masked or block upload.
